## Current State

### Frontend (Next.js 15 + React 19 + TS strict + Tailwind + shadcn/ui)
- Single page (`app/page.tsx`) acts as the role-based router. The Supabase auth session gates entry; on success the user sees a 4-tile profile picker (`use-profile.ts`) that switches role via 4-digit PINs (kitchen=1234, cashier=5678, admin=9999, waiter=0000) loaded from `business_config`.
- Four role views (`components/views/{Waiter,Kitchen,Cashier,Admin}View.tsx`) own their own data via duplicated `useState/useEffect` + Supabase calls. None of them goes through React Query (the package is installed and only used in `BusinessConfigForm.tsx`, with no global `QueryClientProvider` in `app/layout.tsx`).
- State management: three Zustand stores (`store/use-pos-store.ts`, `store/use-cash-register-store.ts`, `store/use-config-store.ts`). Only `use-config-store.ts` uses `persist` middleware. `use-pos-store.ts` mixes table state, cart, orders, analytics, and payment logic into a single 748-line file.
- Realtime wiring is centralized in `lib/supabase/realtime-service.ts` (520 lines). It exposes `subscribeToTables`, `subscribeToOrders`, `subscribeToKitchen`, and `subscribeToPosEvents` (broadcast). It uses a monotonically incrementing `channelCounter` to avoid reusing channel names across re-subscriptions (regression fix for a known @supabase/supabase-js issue).
- `next.config.mjs` has `typescript.ignoreBuildErrors: true` and `eslint.ignoreDuringBuilds: true` — TS and ESLint errors do not break the build.
- `package.json` still names the project `my-v0-project` (v0 boilerplate artifact).
- 100+ `console.log` statements ship to the browser bundle.

### Backend + Realtime (Supabase via @supabase/supabase-js)
- 22 SQL migrations under `supabase/migrations/` cover the full schema (business_config, profiles, tables, categories, dishes, ingredients, ingredient_transactions, cash_registers, cash_transactions, orders, payment_transactions, recipes, recipe_ingredients, promotions, promotion_dishes, dishes bucket, order_items, total_discounts column).
- **No migration adds the tables to the `supabase_realtime` publication.** Without `ALTER PUBLICATION supabase_realtime ADD TABLE ...` the WAL replication that drives `postgres_changes` events never sees these tables — regardless of how cleanly the client subscribes. This is the single most likely root cause of the user's mesa-sync symptom.
- **No Row-Level Security is enabled anywhere** (`grep ENABLE ROW LEVEL` returns zero hits across all migrations). Only the storage bucket policies exist (`storage.objects` SELECT/INSERT/UPDATE/DELETE on bucket `dishes` — including anonymous variants that duplicate the authenticated ones).
- `init.sql` also runs `ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT ALL ON TABLES TO anon; GRANT ALL ON SEQUENCES TO anon;` — every future table is writable by anonymous clients. There is no defense in depth.
- `lib/supabase/client.ts` falls back to a hard-coded `https://xyzcompany.supabase.co` + a checked-in JWT anon key if `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` are missing (line 4–7). Anyone with the public repo has the anon key.
- `service.ts` references `ingredient_transactions_orders` in `deleteOrder` (line 1153) but no migration creates that table — `inventory-control-service.ts:481` does the `insert` only, so deletes of orders with ingredient transactions would currently throw a PostgREST 404.
- `seed.sql` stores plaintext passwords (`carlos123`, `maria123`, `admin123`, `juan123`) in the `profiles.password` column and pins (`kitchen_password=1234`, `cashier_password=5678`, `admin_password=9999`, `waiter_password=0000`) in `business_config`.

### Database
- All 14+ public tables, 22 migrations, but no RLS, no realtime publication, and inconsistent `ON DELETE` behavior:
  - `payment_transactions.cash_register_id` → `CASCADE`
  - `recipes.dish_id` and `recipe_ingredients.*` → `CASCADE`
  - `orders.{parent_order_id, table_id, waiter_id}` → `SET NULL`
  - `order_items.order_id` → **no ON DELETE clause**, so `deleteOrder`/`deletePartialOrder` rely on a manual `from("order_items").delete().eq("order_id", orderId)` step that is **not wrapped in a transaction**.
  - `cash_transactions.cash_register_id` → **no ON DELETE clause**.
  - `ingredient_transactions.ingredient_id` → **no ON DELETE clause**.
- `completePayment` updates the order status to `"paid"` (service.ts:1072) but does **not** persist `payment_method`, `cash_received`, `cash_change`, `tip_amount`, or `cash_register_id` on the order itself (comment on line 1071: "Eliminamos los campos que no existen en el esquema"). All those fields are persisted correctly on the `payment_transactions` row by `cashRegisterService.addTransaction`, but the order row loses that context forever.
- Index coverage is incomplete: `order_items` is filtered by `(order_id, status)` and `(status)` — has indexes; but `payment_transactions` is filtered by `(cash_register_id, timestamp)` and has indexes; no index on `orders.table_id` standalone (only `idx_orders_table` and `idx_orders_table_id`, both on `table_id`, so that's actually fine).

### POS listener (`pos/app.py` — Windows-only Python 3.11)
- 635 lines, no `requirements.txt`, no `pyproject.toml`, no tests, no CI for the Python side. README mentions a `requirements.txt` but the file does not exist on disk.
- Auth = Supabase anon key with `realtime.AsyncRealtimeClient` subscribing to broadcast channels `room_commands` and `room_bills`. Anonymous role is disabled in docker-compose (`ANONYMOUS_USERS_ENABLED: "false"`), so the print listener needs an authenticated session — there's no code path for that. As configured it will silently fail to receive events.
- Credentials are stored via `win32crypt.CryptProtectData` (DPAPI) in `%APPDATA%\VipePOS\credentials.dat`. DPAPI is user-bound — when the user changes their Windows password or runs as a service account, decryption breaks. There's no key rotation.
- USB discovery uses `usb.core.find` with `pyusb` libusb1 backend. On Windows the backend has to be either `libusb-win32` or the WinUSB driver — the installer (`vipe_pos_installer.iss`) does NOT ship a driver and provides no error UX beyond a generic `messagebox.showinfo("Sin USB", ...)`.
- Single outer `while True` retry loop with `await asyncio.sleep(5)` reconnect — fine for the websocket, but no per-printer retry/backoff, no duplicate-print prevention (a re-delivered broadcast prints twice), no command queue, no offline persistence.
- Encoding is hard-coded CP1252 with `errors="replace"` — non-ASCII Spanish accents, dish descriptions, or customer names silently get replaced.
- The `setup_python_env` skill would be the natural setup path but the absence of `requirements.txt` means a developer has to eyeball the README to reproduce the env.

### Build + Infra
- `Dockerfile`: `node:20-alpine`, `npm install --legacy-peer-deps`, copies the whole repo, builds, runs as root (no `USER` directive), exposes 3000, healthcheck on `curl -f http://localhost:3000`.
- `docker-compose.yml` brings up the whole Supabase local stack (db / kong / realtime / meta / studio / rest / storage / auth / app) with a `healthcheck` on `db` and an `app` healthcheck that does NOT wait for db migrations or for Kong to actually accept traffic — the app can boot before Supabase is ready and silently point at the hard-coded fallback URL.
- `docker-compose.prod.yml` is just the app + an optional nginx. No reverse proxy, no SSL, no rate limiting.
- No CI workflow exists (no `.github`, no `.gitlab-ci.yml`).
- The auth flow expects `auth.users` to exist (we use `supabase.auth.signInWithPassword`), but the `profiles` table is not populated by GoTrue; the app manually INSERTs into `profiles` from `seed.sql`. There's no trigger that creates a matching `profiles` row when a new `auth.users` row is created — so a self-service signup creates an auth user with no profile, no role, and no access.

### Docs
- `README.md` references SQL scripts that no longer exist (`create-database-schema.sql`, `create-storage-bucket.sql`, `create-business-config-table.sql`, etc.). Anyone following the setup steps will hit 404s in Studio.
- `DOCKER.md` is accurate but assumes the user knows to run `pnpm docker:dev:seed` after `up -d`. There's no idempotency check.

## Realtime mesa diagnosis (focused)

### Symptoms
- A user reports: "la información de las mesas en tiempo real no se están reflejando corretamente cuando son dispositivos diferentes."
- Three components subscribe to `tables`: `WaiterView.tsx:238`, `TableGrid.tsx:115`, `TableManagementPanel.tsx:55`.
- Each calls `realtimeService.subscribeToTables` (defined at `realtime-service.ts:41-67`) which builds a Postgres channel `tables-changes-<n>-<ts>` listening to `postgres_changes` on `public.tables` with `event: "*"`.

### Likely causes (in order of confidence)

| # | Hypothesis | Evidence | Confidence |
|---|------------|----------|------------|
| 1 | **Tables never added to `supabase_realtime` publication** — `postgres_changes` events never fire regardless of subscription. | `grep -i publication supabase/migrations` returns zero; `ALTER PUBLICATION supabase_realtime ADD TABLE ...` is absent from every migration. The Supabase Realtime worker reads WAL only for tables in this publication. The default publication created by Supabase includes nothing in `public`. | **high** |
| 2 | **RLS silently filtering** — if RLS were enabled, anon clients would receive empty payloads. RLS is currently OFF, so this is unlikely to be the issue today, but it will become one the moment we turn RLS on without a matching policy. | `grep -i "ENABLE ROW LEVEL" supabase/` → no matches. Today: RLS off, so anon sees everything; publication is still the blocker. | low (today) / high (after RLS lands) |
| 3 | **Channel reuse bug + state churn** — `WaiterView` keeps `localChangesRef` to suppress its own events, but on a different device there is no such guard. With the subscription working, every UPDATE from any device reloads ALL tables (`TableGrid.tsx:117-118`); the `loading` flag flickers and the grid blanks for ~half a second per event. That looks exactly like "no se reflejan corretamente". | `TableGrid.tsx:84, 91, 107, 118` — `setLoading(true)` runs on every event. No diffing; full reload on every notification. | medium (only after #1 is fixed) |
| 4 | **Stale closure on `payload.new.waiter_name`** — the `INSERT/UPDATE` handlers in `WaiterView` and `TableGrid` build a `waiter_name` from `payload.new.waiter_name`, but Postgres `postgres_changes` payload's `new` only carries the `waiter_id` (the `waiter_name` is a derived field from the FK join done in `tableService.getAll`). `payload.new.waiter_name` will be `undefined` for the realtime path until we set REPLICA IDENTITY FULL. | `service.ts:180-200` builds `waiter_name` from `profiles` join; the realtime payload has no such join. After #1 is fixed the table grid would show the right status but the wrong waiter name. | medium (only after #1 is fixed) |
| 5 | **Channel leak on role switch** — `WaiterView.tsx:402-411` does `if (tablesSubscriptionRef.current) { tablesSubscriptionRef.current(); ... }`, but the `useCallback` that creates the subscription has `activeTable` in its dependency list (line 412), so any mesa click recreates the subscription. Combined with `uniqueChannelName`, that's fine for memory, but it CAN miss events fired during the brief unsubscribe-resubscribe window. | `WaiterView.tsx:412` — `setupRealtimeSubscriptions` depends on `[setZustandTables, activeTable]`. | low |

### Recommended fix direction (do not implement here)
1. Add `20250917090000_enable_realtime_publication.sql`:
   - `ALTER TABLE public.tables REPLICA IDENTITY FULL;`
   - `ALTER PUBLICATION supabase_realtime ADD TABLE public.tables, public.orders, public.order_items;`
2. Set `REPLICA IDENTITY FULL` on `orders` and `order_items` too so `OLD` payloads carry diffs.
3. In `realtime-service.ts`, change the `tables-changes` filter to a real-time, client-side merge: keep the current array, patch the row from `payload.new`, drop the `loadTables()` reload in `TableGrid.tsx` (let `useTableStore` be the only writer).
4. Run `supabase db reset && pnpm docker:dev:seed` once; in two browser tabs, change `tables.status` from one tab; the other should update within ~500 ms. If it doesn't, suspect the docker image — `supabase/realtime:v2.135.5` needs the extension `wal2json` to be present in `postgis/postgis:16-3.4` (it ships with it) and a publication set on the right slot (Realtime uses `slot_name = supabase_realtime_test_replication_slot` by default in dev).
5. After the symptom is fixed, gate the table grid on a single `useTableStore` and stop the per-component `useState<Table[]>`.

## Open questions for the user

1. **Are you running Supabase locally (`docker-compose up -d`) or against Supabase Cloud?** The `init.sql` only makes sense in the local stack. If you point at Cloud, the realtime publication fix would be applied via the Supabase Dashboard or a different migration.
2. **How many POS stations run simultaneously in a typical shift?** That determines whether the current "reload all tables on every event" approach (HS-08) is good enough or whether we need a proper diff-merge.
3. **Do you have any plans to enable RLS in the short term?** HS-02 is the bigger upstream blocker for any future per-user privacy (multi-restaurant tenants, customer-facing order tracking). If yes, we should bundle the policy work with the realtime fix.
4. **Is there a CI/CD pipeline (GitHub Actions, GitLab CI) on the roadmap?** HS-05 and the missing CI workflow are the root cause of the TS-escape behavior leaking into the codebase; without CI this keeps happening.
5. **Do you have any paid Supabase plan, or is this strictly self-hosted?** This affects which Realtime plan (`Pro` vs `Free`) constraints we need to design around.
6. **Is the printer listener installed on every station, or only on the kitchen computer?** That determines whether HS-12 (anon realtime disabled) is a real blocker or a future concern.
7. **Should the system support multiple restaurants (multi-tenant) or is it strictly a single-tenant deployment?** That changes HS-02, HS-30, and the FK on `auth.users` → `profiles`.
8. **Are the role PINs (1234/5678/9999/0000) in production right now, or only in seed?** They need rotation if the seed has been applied to a real environment.

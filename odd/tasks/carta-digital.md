## Specs

Coordination constraints (L6, L7)
- S0: do not edit `apps/api/src/settings/business-config.ts`, `apps/api/src/cash/**`, `components/printing/**`, `lib/print/**`, `apps/api/src/catalog/{dishes.service,menu.service,catalog.dto}.ts` without first messaging the owning session. Migrations take 0031 or the next free number with a journal `when` greater than the last one, after telling promociones. Carta settings live in their own table, not in `business_config`; per-dish public details (tags, English description) live in their own table, not in `dishes`.

Phase 1 — public read-only menu ("vitrina")
- S1 (L2 "Ruta con slug"): the guest menu is served at `/c/<slug>` (restaurant `slug`) and `/c/<slug>/m/<token>` for a table QR. The token is random per table (never the table number or id); regenerating it invalidates old printed QRs. An unknown slug, a restaurant whose carta is not published, or an unknown/old token shows a not-found page; the table page of an unknown token never reveals another table.
- S2 (tenancy/security): public endpoints need no login and resolve the restaurant only from the slug (and the table only from its token) through dedicated, audited SECURITY DEFINER functions; they never reuse staff functions or fake a user (no guest GUC or guest profile: many write policies check only `restaurant_id`, L12). The guest functions return raw guest-safe rows and the API runs the same TypeScript menu logic the waiter uses (snapshot, promotions, availability) behind a data-source seam, so guest and staff menus cannot drift. They return only guest-safe fields: restaurant name, short description, brand, logo, cover, social links, hours, dayparts, published categories/dishes with list price, active promotion badge/promo price/end per channel (same fields the waiter sees: `promotionBadge`, `promoPrice`, `promotionEndsAt`), availability, tags, English descriptions, modifiers. Never costs, recipes, stock quantities, staff data (beyond the waiter's first name in phase 2) or other customers. Public endpoints are rate-limited.
- S3 (L2 "Un solo estilo elegante"): one single style; the restaurant sets logo, cover, brand color and short description. The brand color is adjusted per theme so text on it passes WCAG AA (artboard `--brand*`). Light/dark follow the phone (`prefers-color-scheme`).
- S4 (01 hero): header shows cover, logo (initials fallback, e.g. "B&L"), name, description, status chip "Abierto · cierra 10:30 pm" / "Cerrado ahora", context chip ("Mesa 12 · Terraza" on a table QR; "Domicilio · 35–45 min" and "Envío $4.000" otherwise), social buttons (Instagram, TikTok, WhatsApp, Google Maps; only the configured ones) and "Compartir".
- S5 (L2 "Carta que se adapta sola"): dayparts (e.g. Desayuno 7:00 am – 11:00 am, Almuerzo 11:30 am – 3:30 pm, Noche 6:00 pm – 10:30 pm) each list their categories; the server decides the current daypart with its own clock in the restaurant timezone. The menu opens on the current daypart; other dayparts can be viewed with the banner "Estás viendo la carta de noche · se pide de 6:00 pm a 10:30 pm." and no add buttons. Outside opening hours: banner "Cerrado ahora" / "Abrimos mañana a las 7:00 am. Puedes ver la carta con calma." and no add buttons. Each daypart may feature a "Plato del día".
- S6 (01): sold-out dishes come automatically from the existing availability (inventory/daily production) and paused (inactive) dishes are hidden; sold-out dishes stay listed at the end of their category with "Agotado hoy" and cannot be added. Active promotions show their badge (e.g. "2x1 hasta 4:00 pm").
- S7 (L5 "Etiquetas del plato"): dish tags Vegetariano, Picante, Sin gluten, Lácteos (set by the restaurant) and "Lo más pedido" (automatic from sales).
- S8 (01 list): search "Buscar en la carta" filters by name/description, with "No hay platos con «q»." and "Borrar búsqueda"; sticky category tabs; dish rows with name, two-line description, price, tags, photo (`image_url`) and a 44 px add button; the dish sheet shows photo, price, description, tags, modifiers (required/optional, price deltas), optional kitchen note, "Compartir" and the add CTA with the live price "Agregar · $42.900".
- S9 (L2 "Plato para compartir", L5 "Redes en la portada"): "Compartir la carta" / "Compartir este plato" open a share sheet with a 9:16 preview (photo, name, price, "Pídelo aquí" / "Ver la carta"), WhatsApp, "Historia" (Web Share API with the image when supported) and "Copiar enlace" (toast "Enlace copiado"). Dish links are `/c/<slug>/p/<dish>` and never carry the table token ("Sin la mesa: quien lo abra ve la carta, no tu cuenta.").
- S10 (L5 "Inglés automático"): the language follows the phone (`Accept-Language`), with an EN/ES switch; dish names stay in Spanish, descriptions use the restaurant's English text (machine-translated, editable in phase 4) with the footer "Automatic translation reviewed by the restaurant."
- S11 (L4 "si esta desactivado solo se trata como una carta"): when table ordering is off, "+" builds a local "Mi lista" ("Muéstrale esta lista a tu mesero"; "La lista vive solo en tu celular: nada se envía a la cocina.").

Phase 2 — table QR
- S12 (L4): table ordering is a per-restaurant setting. When on, a guest can send an order only while the table is open (has an active order); the order arrives as a proposal in the waiter app and goes to the kitchen only when the waiter confirms it ("Nada se cobra ni se cocina hasta que Carolina lo confirme."). Closed table: banner "Para pedir desde aquí, la mesa debe estar abierta" and the send button disabled. The guest sees the proposal status (Enviado, Confirmado, En la cocina, Servido).
- S13 (L3 "Solo informativa", L8): "La cuenta" shows the table's open order read-only, "Partes iguales" (people stepper) or "Por lo que pedí": checking a line shows "Entre [−] N [+] personas" (1–12, "Solo yo" / "Compartido entre N"), the diner's part and the line total; suggested tip "Propina sugerida 10 % (voluntaria)" (from the existing tip setting) toggle; "Te toca $X". Nothing is sent to the cashier ("Es una guía para ustedes").
- S14 (L5 "Reseña al final"): "Pedir la cuenta a Carolina" notifies the waiter (when table ordering is on); then stars and, for every rating, "Escribir una reseña en Google" (no review gating) plus an optional private comment for the restaurant.

Phase 3 — delivery
- S15 (L3 "Nombre + teléfono"): delivery checkout asks Nombre, Celular (7–15 digits), Dirección, Barrio, optional notes and how they pay on delivery (Efectivo with "¿Con cuánto pagas?", Datáfono, Transferencia), shows items, delivery fee (existing delivery fee setting) and total with promotions applied as in the pricing preview. It enters the delivery console as pending; stock and kitchen tickets happen only when the operator confirms. The guest gets "Pedido D-0142 recibido" with status Recibido, Confirmado, En camino, Entregado.
- S16: when online delivery is off, the cart composes a WhatsApp message to the restaurant ("Hola Brasa & Leña, quiero pedir: …") and opens WhatsApp; VIPE receives nothing.

Phase 4 — admin (artboard 02)
- S17: admin page "Ajustes · Carta digital" to publish the carta, edit slug, brand, social links, hours/dayparts, the ordering switches, dish tags, English descriptions and table QR codes (download, regenerate with confirmation).

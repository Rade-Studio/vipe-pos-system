# Feature: migracion-backend-nestjs

Branch `feat/backend-nestjs` (from `origin/dev` 6b119c5, `origin/main` 16de3dd merged in 68231da with no tree change).
Worktree `../vipe-pos-system-worktrees/backend-nestjs`. Engram mirror: `odd/migracion-backend-nestjs/tasks`.
Replace Supabase (hosted and self-hosted) with a NestJS API between the Next.js frontend and a plain Postgres,
keeping realtime, keeping the plpgsql transactional core and RLS, and fixing the structural defects found along the way.

## Specs

- **S1** Migration target: "necesito que me recomiendes el proceso para realizar la migracion de supabase a postgres"
  -> the system runs on plain Postgres with no Supabase service (no GoTrue, PostgREST, Realtime, Storage, Edge Functions, Kong, Studio).
- **S2** Middle layer: "supabase es un servicio muy pesado para alojar en una vps y muy costoso para pagar en supabase, entonces necesito algo intermedio entre el frotend y la BD que sea profesional"
  -> a backend service owns every data access; the browser never holds a database key; the stack fits one VPS: Postgres, API, web, object storage.
- **S3** No regression, no time pressure: "no importa cuanto demoremos, pero no debemos perder, ni el tiempo real"
  -> every behavior the POS has today keeps working, and kitchen, waiter, cashier and delivery screens keep receiving live updates for orders, tables and deliveries without reload. Each module migrates completely before the next starts.
- **S4** Refactor on the way: "de paso refactorizamos lo que se hizo mal desde un principio"
  -> known defects are fixed by design, not patched: components importing the DB client directly (42 in `components/admin`), `(supabase.rpc as any)`, `NEXT_PUBLIC_*` inlined at build time with a production fallback, business rules split between UI and SQL, staff creation through an Edge Function with service role.
- **S5** Backend shape: "avancemos con servicio separado de nestjs"
  -> NestJS runs as its own service and deployable, not inside Next.js.

## Decisions (2026-11-04)

- Separate NestJS service (S5). Web stays at the repository root for now; `apps/api` and `packages/db` join the existing pnpm workspace. Moving web to `apps/web` is a later, optional task.
- Data access: Drizzle ORM over `pg`. SQL migrations stay plain `.sql` files, versioned in `packages/db`, applied by Drizzle's migrator. The 49 Supabase migrations are squashed into one baseline (schema-only dump minus `auth`, `storage`, `realtime`, `extensions` schemas, anon/authenticated grants and the realtime publication).
- Transactional core stays in plpgsql: `pay_order`, `split_order`, `undo_split`, `close_register`, `register_summary`, `create_delivery_order`, `set_delivery_status`, every `inventory_*`/`receive_purchase_order`/`produce_preparation`/`apply_inventory_count`/`save_formula` RPC and every guard trigger. The API calls them inside a transaction. Nothing is rewritten in TypeScript unless a pgTAP test proves the SQL wrong.
- RLS stays as defense in depth. `private.current_restaurant_id()` and `private.current_app_role()` read `current_setting('app.user_id', true)` instead of `auth.uid()`; the API runs `SET LOCAL app.user_id = $1` at the start of every request transaction, connecting as a non-superuser role without `BYPASSRLS`. The 134 policies and the pgTAP suite are kept.
- Auth: own `users` table (replaces `auth.users`; `profiles.auth_user_id` becomes `profiles.user_id`), password hashing with argon2, access JWT in an httpOnly SameSite cookie set by the API plus refresh rotation. Web and API share one domain behind the reverse proxy.
- Realtime: `AFTER INSERT/UPDATE/DELETE` triggers on `orders`, `tables`, `order_deliveries` call `pg_notify` with `{table, op, id, restaurant_id}` only (well under the 8 KB limit). A dedicated `pg` client in the API listens, loads the row, and emits through a socket.io gateway to room `restaurant:<id>` with the same `{eventType, new, old}` shape `postgres_changes` delivers today, so `lib/realtime/order-merge.ts` and `table-merge.ts` stay untouched. Socket auth reuses the cookie JWT.
- Storage: S3-compatible (MinIO on the VPS, or Cloudflare R2). The API issues presigned PUT URLs and stores the object key; public reads go through the bucket URL.
- Contracts: the API publishes OpenAPI; the web consumes a generated typed client (`openapi-typescript` + `openapi-fetch`). No hand-written response types in web.
- Tests: pgTAP against plain Postgres in Docker (`postgres:16` + `pgtap`), replacing `supabase test db`; Vitest for web; Jest (Nest default) or Vitest for the API with Testcontainers for integration. CI gets `api-tests` and keeps `db-tests` on the new runner.
- Delivery stays the user's decision: work-unit commits land on `feat/backend-nestjs` and its chained slices; push, PRs and merges are not performed by the agent.
- T3 (2026-11-04): API specs run on Vitest with `unplugin-swc` (esbuild lacks `emitDecoratorMetadata`, which Nest DI needs), keeping one test runner across the repo. Env validation with zod in `apps/api/src/config/env.ts`, no `@nestjs/config`. Each workspace package pins its own TypeScript 5.x because the root lockfile holds `typescript@5.0.2`. Example env files are named `env.example` (no leading dot), matching the root `env.production.template`; the write tool refuses dotfile env paths. Root `tsconfig.json` excludes `apps/**` and `packages/**` so `pnpm typecheck` keeps covering only web.
- Slice accounting: PRs target `dev`, so review slices (~400 authored lines) are measured against `origin/dev`, not `origin/main`; the 45 dev commits already in this branch are not part of this feature.

## Design: T4 plain-Postgres baseline

Goal: `packages/db` can build the whole schema on a plain `postgres:16` with no Supabase piece, and the pgTAP suite proves tenant isolation and guards still hold through `app.user_id`.

1. **Baseline source.** Start the local Supabase stack (`pnpm supabase db start`, applies the 49 migrations) and dump `pg_dump --schema-only --no-owner --no-privileges --schema=public --schema=private`. Save as the first custom Drizzle migration (`drizzle-kit generate --custom --name baseline`, then paste the SQL; the journal under `packages/db/migrations/meta/` must be committed). Never hand-edit tables beyond the removals below.
2. **Removals.** Every reference to `auth.*`, `storage.*`, `extensions.*`, `graphql*`, `supabase_realtime`, `pgsodium`, `vault`; grants and policies for roles `anon`, `authenticated`, `service_role`; the trigger `on_auth_user_created` and `public.handle_new_user()`; the `dishes` storage bucket migration. Policies that named `authenticated` as the target role become `TO vipe_api`.
3. **Users.** `public.users (id uuid pk default gen_random_uuid(), email citext unique not null, password_hash text not null, password_algo text not null default 'argon2id', is_active boolean not null default true, created_at, updated_at)`. `profiles.auth_user_id` is renamed `user_id` and references `users(id) on delete cascade`. Profile creation moves to the API (T12); no trigger.
4. **Tenant helpers.** New `private.current_user_id()` returns `nullif(current_setting('app.user_id', true), '')::uuid`. `private.current_restaurant_id()` and `private.current_app_role()` resolve through `profiles.user_id = private.current_user_id()`; every other function that called `auth.uid()` calls `private.current_user_id()`. When the setting is absent they return null, so RLS yields no rows.
5. **Roles.** `vipe_api` (LOGIN, NOINHERIT, no BYPASSRLS, no superuser): USAGE on `public` and `private`, SELECT/INSERT/UPDATE/DELETE on all public tables, EXECUTE on the RPCs the web calls today, default privileges for future tables. `vipe_migrator` owns the schema and runs migrations. Roles are created by an idempotent `packages/db/scripts/roles.sql` run by the Docker init, not by a migration.
6. **Runner.** `docker-compose.yml` gains a `db` service built from `packages/db/docker/Dockerfile` (`postgres:16` + `postgresql-16-pgtap`), port 5432, roles init script. `packages/db/scripts/test-db.sh` resets the database, applies migrations with `pnpm db:migrate`, runs every `packages/db/tests/*.test.sql` through `pg_prove` (or `psql` per file with failure detection). Root `pnpm test:db` points to it; the CI `db-tests` job uses the compose service instead of the Supabase CLI. `supabase/` stays untouched until T13 so web development against Supabase keeps working.
7. **pgTAP port.** Copy `supabase/tests/*.test.sql` to `packages/db/tests/`, replacing `request.jwt.claims`/`auth.uid()` impersonation with `SET LOCAL app.user_id = '<uuid>'` and `SET LOCAL ROLE vipe_api`; drop `020_anon_lockdown` cases that only exist because of PostgREST's `anon` role, keep the rest. RED first: a new `005_app_user_setting.test.sql` asserting that without `app.user_id` the helpers return null and `SELECT count(*) FROM orders` as `vipe_api` is 0, and that with it the helpers resolve the seeded profile.

## Design: T5 API core (auth, tenant, transaction per request)

Depends on T4 (users table, `vipe_api` role, `private.current_user_id()`).

0. **Drizzle schema.** Run `drizzle-kit pull` against a migrated database to generate `packages/db/src/schema/*.ts` from the baseline (T4 left `src/schema/index.ts` empty on purpose). Commit the generated files; regenerate after every later SQL migration. Typed queries in the API import tables from `@vipe/db`.
1. **DbModule.** Global module creating `createDb(env.databaseUrl)` from `@vipe/db` once, connected as `vipe_api`, closed on shutdown.
1b. **Close the T4 open risk first.** The baseline grants `vipe_api` SELECT/INSERT/UPDATE/DELETE on `public.users` with no RLS, so it can read `password_hash`. The T5 migration revokes that grant and re-grants column-level SELECT on `id, email, is_active, created_at, updated_at` plus INSERT/UPDATE through `SECURITY DEFINER` helpers only (`private.create_user`, `private.set_password`), with a pgTAP test proving `vipe_api` cannot read `password_hash`.
2. **Unit of work.** An interceptor opens one transaction per authenticated HTTP request: `pool.connect()`, `BEGIN`, `SELECT set_config('app.user_id', $1, true)` with the authenticated user id, stores the Drizzle instance bound to that client in `AsyncLocalStorage`, `COMMIT` on success and `ROLLBACK` on any thrown error, always releasing the client. Services read the current database through an injectable `UnitOfWork.db`; nothing else holds a client. Public routes (health, login, refresh) run outside the unit of work.
3. **Login lookup without exposing hashes.** New migration adds `auth_sessions (id uuid pk, user_id fk users on delete cascade, refresh_hash text unique not null, expires_at timestamptz not null, revoked_at timestamptz, created_at)` and a `SECURITY DEFINER` function `private.find_user_for_login(p_email citext)` returning `(id, password_hash, password_algo, is_active)`, granted to `vipe_api`; `vipe_api` keeps SELECT on `users` only for `id, email, is_active, created_at, updated_at`. `auth_sessions` has RLS keyed on `user_id = private.current_user_id()` plus INSERT/UPDATE by the API through `SECURITY DEFINER` helpers `private.create_session`, `private.rotate_session`, `private.revoke_session`.
4. **Passwords.** `argon2` (argon2id) for new hashes. `password_algo = 'bcrypt'` rows (imported from GoTrue in T14) verify with `bcryptjs` and are re-hashed to argon2id on the first successful login.
5. **Tokens.** Access JWT with `jose`, HS256, `JWT_SECRET` (min 32 chars) from env, 15 min, claims `sub` (user id) and `sid` (session id) only; tenant and role are resolved per request from `profiles` inside the unit of work, never trusted from the token. Cookies: `vipe_access` (httpOnly, SameSite=Lax, Secure when `COOKIE_SECURE=true`, path `/`), `vipe_refresh` (same flags, path `/api/auth`, 30 days, opaque 32-byte random, stored as sha256). Refresh rotates the session: the old refresh token is rejected after use.
6. **Endpoints.** `POST /api/auth/login {email, password}` -> 200 `{user: {id, email}, profile: {id, name, role, restaurantId}}` and both cookies; 401 `Invalid credentials` for unknown email, wrong password or inactive user, with identical timing paths. `POST /api/auth/refresh` -> 204 and rotated cookies; 401 when missing, expired, revoked or reused. `POST /api/auth/logout` -> 204, revokes the session and clears cookies. `GET /api/auth/me` -> 200 same body as login; 401 without a valid access cookie.
7. **Guards.** Global `AuthGuard` reading `vipe_access`, verifying the JWT and attaching `{userId, sessionId}`; `@Public()` opts a route out. `RolesGuard` with `@Roles(...)` compares against `private.current_app_role()` resolved in the unit of work. A user without a profile gets 403.
8. **Errors.** One exception filter returning `{statusCode, error, message}`; Postgres mapping: `23505` -> 409, `42501` -> 403, `23514`/`23503`/`22P02` -> 422, `P0001` (RAISE EXCEPTION from the RPCs) -> 422 with the raised message verbatim. Unknown errors -> 500 without leaking the driver message.
9. **Env.** Add `JWT_SECRET` (required, min 32), `COOKIE_SECURE` (boolean, default `true`), `ACCESS_TOKEN_TTL_SECONDS` (default 900), `REFRESH_TOKEN_TTL_SECONDS` (default 2592000) to `parseEnv` with tests, and to `apps/api/env.example`.
10. **Tests (Testcontainers).** `@testcontainers/postgresql` starts the `packages/db/docker` image, runs `roles.sql` and the migrator, seeds one restaurant with an admin profile and a waiter profile plus a second restaurant. Specs: login success sets both cookies and returns the profile; wrong password, unknown email and inactive user return 401 with the same body; `me` without cookie 401, with cookie 200; refresh rotates and the previous refresh token is rejected; logout revokes and a later refresh is 401; tenant isolation: a probe route under test only (`GET /api/_test/orders-count`, registered solely in the spec module) returns restaurant A's count for A's user and 0 rows for a user of restaurant B; a route with `@Roles('admin')` returns 403 for the waiter.

## Migration order and strangler rule

The web keeps working against Supabase until a module is fully served by the API; the swap happens behind the existing service boundary (`lib/supabase/<module>-service.ts` -> `lib/api/<module>.ts`) one module at a time, and the Supabase path for that module is deleted in the same slice. Order: catalog (read-heavy, low risk) -> tables and orders with realtime (core) -> payments and register -> inventory -> delivery -> staff, profiles, storage -> remove Supabase -> data migration and cut-over.

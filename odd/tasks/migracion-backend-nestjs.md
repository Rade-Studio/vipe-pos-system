# Feature: migracion-backend-nestjs

Branch `feat/backend-nestjs` (from `origin/dev` 6b119c5, `origin/main` 16de3dd merged in 68231da with no tree change).
Worktree `../vipe-pos-system-worktrees/backend-nestjs`. Engram mirror: `odd/migracion-backend-nestjs/tasks`.
Replace Supabase (hosted and self-hosted) with a NestJS API between the Next.js frontend and a plain Postgres,
keeping realtime, keeping the plpgsql transactional core and RLS, and fixing the structural defects found along the way.

## Specs

- **S1** Migration target: "necesito que me recomiendes el proceso para realizar la migracion de supabase a postgres"
  -> the system runs on plain Postgres with no Supabase service (no GoTrue, PostgREST, Realtime, Storage, Edge Functions, Kong, Studio).
- **S2** Middle layer: "supabase es un servicio muy pesado para alojar en una vps y muy costoso para pagar en supabase, entonces necesito algo intermedio entre el frotend y la BD que sea profesional"
  -> a backend service owns every data access; the browser never holds a database key; the stack fits one VPS: Postgres, API, web, object storage.
- **S3** No regression, no time pressure: "no importa cuanto demoremos, pero no debemos perder, ni el tiempo real"
  -> every behavior the POS has today keeps working, and kitchen, waiter, cashier and delivery screens keep receiving live updates for orders, tables and deliveries without reload. Each module migrates completely before the next starts.
- **S4** Refactor on the way: "de paso refactorizamos lo que se hizo mal desde un principio"
  -> known defects are fixed by design, not patched: components importing the DB client directly (42 in `components/admin`), `(supabase.rpc as any)`, `NEXT_PUBLIC_*` inlined at build time with a production fallback, business rules split between UI and SQL, staff creation through an Edge Function with service role.
- **S5** Backend shape: "avancemos con servicio separado de nestjs"
  -> NestJS runs as its own service and deployable, not inside Next.js.

## Decisions (2026-11-04)

- Separate NestJS service (S5). Web stays at the repository root for now; `apps/api` and `packages/db` join the existing pnpm workspace. Moving web to `apps/web` is a later, optional task.
- Data access: Drizzle ORM over `pg`. SQL migrations stay plain `.sql` files, versioned in `packages/db`, applied by Drizzle's migrator. The 49 Supabase migrations are squashed into one baseline (schema-only dump minus `auth`, `storage`, `realtime`, `extensions` schemas, anon/authenticated grants and the realtime publication).
- Transactional core stays in plpgsql: `pay_order`, `split_order`, `undo_split`, `close_register`, `register_summary`, `create_delivery_order`, `set_delivery_status`, every `inventory_*`/`receive_purchase_order`/`produce_preparation`/`apply_inventory_count`/`save_formula` RPC and every guard trigger. The API calls them inside a transaction. Nothing is rewritten in TypeScript unless a pgTAP test proves the SQL wrong.
- RLS stays as defense in depth. `private.current_restaurant_id()` and `private.current_app_role()` read `current_setting('app.user_id', true)` instead of `auth.uid()`; the API runs `SET LOCAL app.user_id = $1` at the start of every request transaction, connecting as a non-superuser role without `BYPASSRLS`. The 134 policies and the pgTAP suite are kept.
- Auth: own `users` table (replaces `auth.users`; `profiles.auth_user_id` becomes `profiles.user_id`), password hashing with argon2, access JWT in an httpOnly SameSite cookie set by the API plus refresh rotation. Web and API share one domain behind the reverse proxy.
- Realtime: `AFTER INSERT/UPDATE/DELETE` triggers on `orders`, `tables`, `order_deliveries` call `pg_notify` with `{table, op, id, restaurant_id}` only (well under the 8 KB limit). A dedicated `pg` client in the API listens, loads the row, and emits through a socket.io gateway to room `restaurant:<id>` with the same `{eventType, new, old}` shape `postgres_changes` delivers today, so `lib/realtime/order-merge.ts` and `table-merge.ts` stay untouched. Socket auth reuses the cookie JWT.
- Storage: S3-compatible (MinIO on the VPS, or Cloudflare R2). The API issues presigned PUT URLs and stores the object key; public reads go through the bucket URL.
- Contracts: the API publishes OpenAPI; the web consumes a generated typed client (`openapi-typescript` + `openapi-fetch`). No hand-written response types in web.
- Tests: pgTAP against plain Postgres in Docker (`postgres:16` + `pgtap`), replacing `supabase test db`; Vitest for web; Jest (Nest default) or Vitest for the API with Testcontainers for integration. CI gets `api-tests` and keeps `db-tests` on the new runner.
- Delivery stays the user's decision: work-unit commits land on `feat/backend-nestjs` and its chained slices; push, PRs and merges are not performed by the agent.
- T3 (2026-11-04): API specs run on Vitest with `unplugin-swc` (esbuild lacks `emitDecoratorMetadata`, which Nest DI needs), keeping one test runner across the repo. Env validation with zod in `apps/api/src/config/env.ts`, no `@nestjs/config`. Each workspace package pins its own TypeScript 5.x because the root lockfile holds `typescript@5.0.2`. Example env files are named `env.example` (no leading dot), matching the root `env.production.template`; the write tool refuses dotfile env paths. Root `tsconfig.json` excludes `apps/**` and `packages/**` so `pnpm typecheck` keeps covering only web.
- Slice accounting: `feat/backend-nestjs` is the integration branch; chained PRs target it and are measured against it, and the final PR targets `dev` after T14. The 45 dev commits already in this branch are not part of this feature.

## Design: T4 plain-Postgres baseline

Goal: `packages/db` can build the whole schema on a plain `postgres:16` with no Supabase piece, and the pgTAP suite proves tenant isolation and guards still hold through `app.user_id`.

1. **Baseline source.** Start the local Supabase stack (`pnpm supabase db start`, applies the 49 migrations) and dump `pg_dump --schema-only --no-owner --no-privileges --schema=public --schema=private`. Save as the first custom Drizzle migration (`drizzle-kit generate --custom --name baseline`, then paste the SQL; the journal under `packages/db/migrations/meta/` must be committed). Never hand-edit tables beyond the removals below.
2. **Removals.** Every reference to `auth.*`, `storage.*`, `extensions.*`, `graphql*`, `supabase_realtime`, `pgsodium`, `vault`; grants and policies for roles `anon`, `authenticated`, `service_role`; the trigger `on_auth_user_created` and `public.handle_new_user()`; the `dishes` storage bucket migration. Policies that named `authenticated` as the target role become `TO vipe_api`.
3. **Users.** `public.users (id uuid pk default gen_random_uuid(), email citext unique not null, password_hash text not null, password_algo text not null default 'argon2id', is_active boolean not null default true, created_at, updated_at)`. `profiles.auth_user_id` is renamed `user_id` and references `users(id) on delete cascade`. Profile creation moves to the API (T12); no trigger.
4. **Tenant helpers.** New `private.current_user_id()` returns `nullif(current_setting('app.user_id', true), '')::uuid`. `private.current_restaurant_id()` and `private.current_app_role()` resolve through `profiles.user_id = private.current_user_id()`; every other function that called `auth.uid()` calls `private.current_user_id()`. When the setting is absent they return null, so RLS yields no rows.
5. **Roles.** `vipe_api` (LOGIN, NOINHERIT, no BYPASSRLS, no superuser): USAGE on `public` and `private`, SELECT/INSERT/UPDATE/DELETE on all public tables, EXECUTE on the RPCs the web calls today, default privileges for future tables. `vipe_migrator` owns the schema and runs migrations. Roles are created by an idempotent `packages/db/scripts/roles.sql` run by the Docker init, not by a migration.
6. **Runner.** `docker-compose.yml` gains a `db` service built from `packages/db/docker/Dockerfile` (`postgres:16` + `postgresql-16-pgtap`), port 5432, roles init script. `packages/db/scripts/test-db.sh` resets the database, applies migrations with `pnpm db:migrate`, runs every `packages/db/tests/*.test.sql` through `pg_prove` (or `psql` per file with failure detection). Root `pnpm test:db` points to it; the CI `db-tests` job uses the compose service instead of the Supabase CLI. `supabase/` stays untouched until T13 so web development against Supabase keeps working.
7. **pgTAP port.** Copy `supabase/tests/*.test.sql` to `packages/db/tests/`, replacing `request.jwt.claims`/`auth.uid()` impersonation with `SET LOCAL app.user_id = '<uuid>'` and `SET LOCAL ROLE vipe_api`; drop `020_anon_lockdown` cases that only exist because of PostgREST's `anon` role, keep the rest. RED first: a new `005_app_user_setting.test.sql` asserting that without `app.user_id` the helpers return null and `SELECT count(*) FROM orders` as `vipe_api` is 0, and that with it the helpers resolve the seeded profile.

## Design: T5 API core (auth, tenant, transaction per request)

Depends on T4 (users table, `vipe_api` role, `private.current_user_id()`).

0. **Drizzle schema.** Run `drizzle-kit pull` against a migrated database to generate `packages/db/src/schema/*.ts` from the baseline (T4 left `src/schema/index.ts` empty on purpose). Commit the generated files; regenerate after every later SQL migration. Typed queries in the API import tables from `@vipe/db`.
1. **DbModule.** Global module creating `createDb(env.databaseUrl)` from `@vipe/db` once, connected as `vipe_api`, closed on shutdown.
1b. **Close the T4 open risk first.** The baseline grants `vipe_api` SELECT/INSERT/UPDATE/DELETE on `public.users` with no RLS, so it can read `password_hash`. The T5 migration revokes that grant and re-grants column-level SELECT on `id, email, is_active, created_at, updated_at` plus INSERT/UPDATE through `SECURITY DEFINER` helpers only (`private.create_user`, `private.set_password`), with a pgTAP test proving `vipe_api` cannot read `password_hash`.
2. **Unit of work.** An interceptor opens one transaction per authenticated HTTP request: `pool.connect()`, `BEGIN`, `SELECT set_config('app.user_id', $1, true)` with the authenticated user id, stores the Drizzle instance bound to that client in `AsyncLocalStorage`, `COMMIT` on success and `ROLLBACK` on any thrown error, always releasing the client. Services read the current database through an injectable `UnitOfWork.db`; nothing else holds a client. Public routes (health, login, refresh) run outside the unit of work.
3. **Login lookup without exposing hashes.** New migration adds `auth_sessions (id uuid pk, user_id fk users on delete cascade, refresh_hash text unique not null, expires_at timestamptz not null, revoked_at timestamptz, created_at)` and a `SECURITY DEFINER` function `private.find_user_for_login(p_email citext)` returning `(id, password_hash, password_algo, is_active)`, granted to `vipe_api`; `vipe_api` keeps SELECT on `users` only for `id, email, is_active, created_at, updated_at`. `auth_sessions` has RLS keyed on `user_id = private.current_user_id()` plus INSERT/UPDATE by the API through `SECURITY DEFINER` helpers `private.create_session`, `private.rotate_session`, `private.revoke_session`.
4. **Passwords.** `argon2` (argon2id) for new hashes. `password_algo = 'bcrypt'` rows (imported from GoTrue in T14) verify with `bcryptjs` and are re-hashed to argon2id on the first successful login.
5. **Tokens.** Access JWT with `jose`, HS256, `JWT_SECRET` (min 32 chars) from env, 15 min, claims `sub` (user id) and `sid` (session id) only; tenant and role are resolved per request from `profiles` inside the unit of work, never trusted from the token. Cookies: `vipe_access` (httpOnly, SameSite=Lax, Secure when `COOKIE_SECURE=true`, path `/`), `vipe_refresh` (same flags, path `/api/auth`, 30 days, opaque 32-byte random, stored as sha256). Refresh rotates the session: the old refresh token is rejected after use.
6. **Endpoints.** `POST /api/auth/login {email, password}` -> 200 `{user: {id, email}, profile: {id, name, role, restaurantId}}` and both cookies; 401 `Invalid credentials` for unknown email, wrong password or inactive user, with identical timing paths. `POST /api/auth/refresh` -> 204 and rotated cookies; 401 when missing, expired, revoked or reused. `POST /api/auth/logout` -> 204, revokes the session and clears cookies. `GET /api/auth/me` -> 200 same body as login; 401 without a valid access cookie.
7. **Guards.** Global `AuthGuard` reading `vipe_access`, verifying the JWT and attaching `{userId, sessionId}`; `@Public()` opts a route out. `RolesGuard` with `@Roles(...)` compares against `private.current_app_role()` resolved in the unit of work. A user without a profile gets 403.
8. **Errors.** One exception filter returning `{statusCode, error, message}`; Postgres mapping: `23505` -> 409, `42501` -> 403, `23514`/`23503`/`22P02` -> 422, `P0001` (RAISE EXCEPTION from the RPCs) -> 422 with the raised message verbatim. Unknown errors -> 500 without leaking the driver message.
9. **Env.** Add `JWT_SECRET` (required, min 32), `COOKIE_SECURE` (boolean, default `true`), `ACCESS_TOKEN_TTL_SECONDS` (default 900), `REFRESH_TOKEN_TTL_SECONDS` (default 2592000) to `parseEnv` with tests, and to `apps/api/env.example`.
10. **Tests (Testcontainers).** `@testcontainers/postgresql` starts the `packages/db/docker` image, runs `roles.sql` and the migrator, seeds one restaurant with an admin profile and a waiter profile plus a second restaurant. Specs: login success sets both cookies and returns the profile; wrong password, unknown email and inactive user return 401 with the same body; `me` without cookie 401, with cookie 200; refresh rotates and the previous refresh token is rejected; logout revokes and a later refresh is 401; tenant isolation: a probe route under test only (`GET /api/_test/orders-count`, registered solely in the spec module) returns restaurant A's count for A's user and 0 rows for a user of restaurant B; a route with `@Roles('admin')` returns 403 for the waiter.

## Design: T6 realtime (pg_notify -> NestJS listener -> socket.io rooms)

Depends on T5 (auth cookie, unit of work, `@vipe/db` schema). Web-side swap of `lib/supabase/realtime-service.ts` belongs to T8; T6 delivers database + API only.

1. **Payload builder, testable.** New migration adds `private.change_payload(p_table text, p_op text, p_new jsonb, p_old jsonb) RETURNS jsonb` (IMMUTABLE, `SET search_path = ''`) returning `{"table", "op", "id", "restaurant_id"}` from `coalesce(p_new, p_old)`; and the trigger function `private.notify_change()` (`SET search_path = ''`) that calls `pg_notify('pos_changes', private.change_payload(TG_TABLE_NAME, TG_OP, to_jsonb(NEW), to_jsonb(OLD))::text)`. Triggers `AFTER INSERT OR UPDATE OR DELETE FOR EACH ROW` named `notify_change` on `public.orders`, `public.tables`, `public.order_deliveries`. Correction (2026-11-04, worker finding): `orders`, `tables` and `order_deliveries` are `REPLICA IDENTITY FULL` in the baseline, so today's Supabase UPDATE/DELETE events carry the full `old` row and `lib/delivery/realtime.ts` relies on `old.order_type` on DELETE. To keep S3, `change_payload` includes `"old": to_jsonb(OLD)` for UPDATE and DELETE when the payload stays at or under 7000 bytes; otherwise `old` falls back to the key columns (`id` or `order_id`, `restaurant_id`, `order_type` when present) plus `"old_truncated": true`. `new` is never in the NOTIFY payload; the listener loads it through `realtime_row`. `order_deliveries` has no `id`: its key is `order_id`, used as the payload `id` and by `realtime_row`. The kitchen screen also subscribes to `order_items`; that trigger belongs to T8 (orders module), not T6. pgTAP `170_realtime_notify.test.sql`: the three triggers exist (this restores the check dropped with the `supabase_realtime` publication), both functions pin `search_path`, `change_payload` returns the exact JSON for INSERT (new only), UPDATE (new), DELETE (old only) inputs via `results_eq`/`is`.
2. **Row loader for fan-out.** `private.realtime_row(p_table text, p_id uuid) RETURNS jsonb` (SECURITY DEFINER, `SET search_path = ''`, `GRANT EXECUTE TO vipe_api`) returns `to_jsonb(row)` for exactly `orders`, `tables`, `order_deliveries` and raises `22023` for any other table. This is the one deliberate cross-tenant read `vipe_api` gets, by primary key, on three tables, documented in the function comment; pgTAP asserts the whitelist and that `vipe_api` can execute it while a plain `SELECT` on those tables as `vipe_api` without `app.user_id` still returns no rows.
3. **Listener.** `RealtimeModule` with `PgListenerService`: one dedicated `pg.Client` (never the pool) connected as `vipe_api`, `LISTEN pos_changes`, parses each notification JSON, loads the row through `private.realtime_row` for INSERT/UPDATE (DELETE carries only `{id, restaurant_id}` as `old`, matching `postgres_changes` without `REPLICA IDENTITY FULL`), and hands an event to the gateway. Reconnect on `error`/`end` with exponential backoff 1 s to 30 s; after every successful reconnect emit `resync` to every room so clients refetch, which is what the web does today on channel re-subscribe. Started in `onModuleInit`, stopped in `onModuleDestroy`.
4. **Gateway.** `@nestjs/platform-socket.io` + `@nestjs/websockets`, namespace `/realtime`, CORS `env.webOrigin` with credentials. On connection: read `vipe_access` from the handshake cookie header, verify the JWT with the T5 token service, resolve `restaurantId` through a unit of work (`SET LOCAL app.user_id`, `private.current_restaurant_id()`), join room `restaurant:<restaurantId>`; disconnect with reason `unauthorized` otherwise. Event name `pos_changes`, payload shape identical to Supabase's `RealtimePostgresChangesPayload`: `{schema: 'public', table, commit_timestamp, eventType: 'INSERT'|'UPDATE'|'DELETE', new, old, errors: null}` so `lib/realtime/order-merge.ts` and `table-merge.ts` consume it unchanged.
5. **Specs (Testcontainers, like T5).** Connect `socket.io-client` with the login cookie of a restaurant A user and one of restaurant B; insert, update and delete an order for A directly in the database; assert A receives three `pos_changes` events with the exact shape and B receives none; assert a socket without a valid cookie is disconnected; assert that terminating the listener's backend connection (`pg_terminate_backend` from the superuser) leads to a reconnect and one `resync` event.
6. **Docs.** `docs/arquitectura-backend.md` section 4.5 gets the event shape and the `realtime_row` exception; README backend subsection lists the socket namespace.

## Design: T8 tables and orders (API T8a, web T8b, printing bridge T8c)

Source map: explorer report 2026-11-04 (`lib/supabase/service.ts:96-678` tableService/orderService, `lib/supabase/realtime-service.ts`, `lib/realtime/*`, `lib/cashier/orders.ts`, `lib/kitchen/order.ts`, `lib/admin/orders.ts`, `store/useOrderStore.ts`, Waiter/Kitchen/Cashier/Admin views, `components/admin/tables/TableManagementPanel.tsx`, `lib/supabase/inventory/sales-service.ts`).

### T8a API
1. **Orders read.** `GET /orders?status=active,kitchen,delivered&include=items,table,waiter` returns camelCase `Order` DTOs with `items` embedded in one SQL query (`json_agg`), ordered by `createdAt desc`; `include=table,waiter` adds `tableNumber` and `waiterName` for the admin list. `GET /orders/:id` same shape. No pagination today; the API caps at 500 rows and documents it.
2. **Orders write, one transaction each.** `POST /orders {tableId, waiterId, orderType, items:[{dishId, quantity, unitPrice?, comments}], tipPercentage?, force?}`: validates every dish belongs to the tenant and is active, prices every item server-side from the catalog with active promotions (`unitPrice`, when sent, is the price the client showed: a mismatch answers 409 `Price changed` with the current prices and writes nothing), refuses a second open order on the same table (409) and accepts only `orderType: dine_in` until T11, inserts the order with status `kitchen` and server timestamps, inserts the items with status `kitchen`, calls `private.recompute_order_bill(order_id)` (the same function `pay_order` trusts) instead of client-side totals, runs `check_dishes_stock` when inventory control is enabled and returns 409 `{shortages}` unless `force: true`, then `consume_order_stock`, then table status `kitchen`. Returns the order with items. `POST /orders/:id/items {items, force?}`: same validations, inserts, `recompute_order_bill`, status back to `kitchen`, stock check/consume, table `kitchen`. `PATCH /orders/:id/status {status}`: only `kitchen -> delivered` (kitchen/waiter/admin); `delivered` sets the table to `served`; `paid` and `cancelled` are rejected with 422 (`paid` only through `pay_order`). `POST /orders/:id/items/served {itemIds}` (kitchen): items -> `served`; when no `kitchen` item remains, the order becomes `delivered` and its table `served`, atomically. `DELETE /orders/:id` (admin): `delete_order_with_items` then table `available` with `waiterId null`, one transaction.
3. **Tables.** `GET /tables` (ordered by number, with `waiterName` from profiles), `POST /tables`, `PATCH /tables/:id {number?, status?, waiterId?}` (admin), `DELETE /tables/:id` -> 409 `Table has open orders` when any order of the table is not `paid`. `POST /tables/:id/assign {waiterId}` -> `occupied`; `POST /tables/:id/release` -> `available` and `waiterId null`, rejected with 409 when the table is `kitchen`, `delivered`, `served` or `reserved` unless the caller is admin with `force: true` (moves the client-side guard of `WaiterView:603-611` to the server). Every write sets `updated_at` server-side; clients never send timestamps (removes the clock-drift hole in `mergeTableList`).
4. **Waiters list.** `GET /staff/waiters` (profiles with role `waiter`, active) for `hooks/use-waiters.ts` and the portal; full staff management stays in T12.
5. **Realtime additions.** New migration: `notify_change` trigger on `public.order_items` (its payload `restaurant_id` comes from the row) and `order_items` added to the `realtime_row` whitelist, with pgTAP. Server-side enrichment in the listener replaces two client N+1 patterns: `orders` INSERT/UPDATE events carry `new.order_items` (one query per event, server-side, as `realtime-service.ts:249` did per client), and `tables` events carry `new.waiter_name` (so `TableManagementPanel` stops calling `getById` per event). `order_items` events carry full `old` (triggers always have OLD), which the kitchen needs for `old.status`.
6. **Specs.** Integration per endpoint with tenant isolation and role rejection; transactional cases (item insert failure rolls back the order; shortage without `force` leaves no order and no stock movement; `served` on the last item flips order and table); 409 cases; realtime enrichment cases.

### T8b web swap
1. **One mapper.** `lib/api/orders.ts` exposes `toOrder(dto)` and the five duplicate mappers (`WaiterView:148-183`, `lib/cashier/orders.ts:116`, `lib/kitchen/order.ts:47`, `lib/admin/orders.ts`, `store/useOrderStore.ts:69-100`) are deleted in favour of it; the kitchen keeps its `kitchen`-items projection as a pure function over `Order`.
2. **Services.** `lib/api/orders.ts` and `lib/api/tables.ts` replace `orderService`/`tableService` with the same function names the views call; `lib/api/realtime.ts` replaces `realtime-service.ts` with the same `subscribeToTables/subscribeToOrders/subscribeToKitchen` signatures over one `socket.io-client` connection (`/realtime`, `withCredentials`), feeding the unchanged `order-merge.ts`/`table-merge.ts`; on `resync` and on socket reconnect it invalidates `['orders', ...]`, `['tables']` and the kitchen query (today nothing refetches on reconnect; this closes the lost-notification window). After an auth refresh the socket reconnects. Dev proxy note (T7 finding): Next redirects `/socket.io/?EIO=4...` to `/socket.io?...` with 308 because it strips trailing slashes; T8b sets `addTrailingSlash: false` on both socket.io ends (or `skipTrailingSlashRedirect` in `next.config.mjs`) and verifies the WebSocket upgrade through the Next rewrite in dev; production routes `/socket.io` at the reverse proxy.
3. **Views.** Waiter: create/add-items/release call the API, drop `consume_order_stock` and `check_dishes_stock` client calls (now inside `POST /orders`), keep the shortage dialog driven by the 409 body, keep echo suppression. Kitchen: `served` through the API (removes the two direct Supabase writes at `KitchenView:466,555`), coalescer unchanged. Cashier and Admin: list through the API, admin delete through `DELETE /orders/:id`. `TableManagementPanel` uses `PATCH /tables/:id` and the enriched events. `store/useOrderStore.loadOrders` becomes one request with three statuses.
4. **Delete** `orderService`, `tableService`, `waiterService`, `realtimeService` (except the broadcast functions, see T8c), `lib/admin/orders.ts` direct select, `lib/supabase/inventory/sales-service.ts` callers for orders. Update the mocking tests listed by the explorer (Waiter/Kitchen/Cashier/Admin view tests, `order-apply`, `table-fanout`, `page.test.tsx`, `useOrderStore.test.ts`, `TableManagementPanel.test.tsx`, `realtime-service.test.ts` replaced by `lib/api/realtime.test.ts`).
5. **Verification.** Dev stack: two browsers (waiter and kitchen) see each other's changes live; cashier list updates on item add; admin delete releases the table; no request to Supabase from these screens (network panel).

### T8c printing bridge
Source map (explorer 2026-11-04): `pos/app.py:180-190,460-466` listens with a service-role token on the global channels `room_bills` and `room_commands`, so every restaurant's tickets reach every printer (no tenant isolation); tickets are fire-and-forget (lost when the listener is offline, only `pos/dedupe.py` dedupes by `invoiceNumber`); `realtime` is not pinned in `pos/requirements.txt`; payloads are `{invoiceNumber, invoice: PrintableInvoice, displayItems}` for `new_invoice` (`realtime-service.ts:181-202`, type `types/index.ts:206-248`) and `CommandPayload {invoiceNumber, items, waiter, table?, delivery?}` for `new_command` (`:204-222`); `handle_comanda` requires `invoiceNumber`, `items`, `waiter`; command `invoiceNumber` is `Math.random()` (`WaiterView.tsx:860`).

1. **Printer identity.** Table `printer_tokens (id, restaurant_id, name, token_hash, created_at, revoked_at, last_seen_at)` with RLS by tenant; admin endpoints `POST /devices/printers {name}` (returns the plaintext token once), `GET /devices/printers`, `DELETE /devices/printers/:id`. The socket handshake accepts `auth: {token}`; the gateway hashes it, resolves the restaurant, joins `printers:<restaurantId>` and updates `last_seen_at`. Cookies are not used by the headless service.
2. **Durable queue.** Table `print_jobs (id, restaurant_id, kind invoice|command, payload jsonb, created_at, printed_at, printer_token_id)`. `POST /print/invoices {invoice, displayItems}` and `POST /print/commands {items, waiter, table?, delivery?}` (any role) insert a job in the request transaction and, after commit, emit `print_job {id, kind, payload}` to the printers room. ## Migration order and strangler rule

Correction (2026-11-04, after the T7 exploration): a runtime strangler across two databases is impossible for a POS (orders reference dishes, payments reference orders), and no module can call the API without the API session cookie. So the swap is a **code strangler on the integration branch**: `feat/backend-nestjs` is the integration branch, chained PRs target it (not `dev`), the branch is not deployable between T7 and T13, and one final PR brings the whole backend into `dev` after T14's rehearsal. Each module still migrates completely, behind the existing service boundary (`lib/supabase/<module>-service.ts` -> `lib/api/<module>.ts`), deleting its Supabase path in the same slice, and is verified on its own screens against the plain-Postgres dev stack (`pnpm db:dev` seed). Order: web foundation and auth swap (T7) -> catalog (T7b) -> tables and orders with realtime (T8) -> payments and register -> inventory -> delivery -> staff, profiles, storage -> remove Supabase -> data migration and cut-over.
